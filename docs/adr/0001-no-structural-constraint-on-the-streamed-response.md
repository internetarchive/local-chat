# Keep the streamed response unconstrained; generate Follow-ups/Icebreakers via a separate call

The obvious-looking design for producing a chat reply and a set of
suggested next questions in one shot would be a single call: stream the
answer, and ask for structured suggestions to ride along with it. That
doesn't actually work with a structural output constraint on the
underlying on-device model API — a constraint applies to the *entire*
response from the first token, not to a trailing portion of it.

## Decision

The streamed reply itself never carries a structural output constraint —
it's plain, free-flowing markdown prose from start to finish. Follow-ups
and Icebreakers are generated by a separate, non-streaming call
constrained to a JSON array of strings, fired only after the streamed
reply has finished (for Follow-ups) or once the assistant's grounding is
primed (for Icebreakers).

## Considered Options

- **One constrained call producing both the reply and the suggestions.**
  Rejected: forcing the entire response into a schema (e.g.
  `{ "reply": string, "followups": string[] }`) means the reply text
  itself is now trapped inside a JSON string value, which either kills
  natural streaming markdown rendering entirely or requires incrementally
  parsing partial JSON to extract a still-being-written string field —
  real complexity for no benefit, chasing an optimization that doesn't
  apply here.
- **A trailing markdown "block" in the same streamed response** (e.g., a
  fenced code block at the end containing suggestion data), parsed out
  after the fact. Considered and rejected: it still requires detecting
  and hiding an in-progress, not-yet-complete trailing block from the
  renderer while it's streaming in, and gains little over just doing a
  second call, since Follow-ups depend on the reply's actual content
  anyway and can't be produced meaningfully before that content exists.
- **Two separate calls (chosen).** The reply streams as plain prose with
  no constraint at all. Follow-ups/Icebreakers get their own call,
  constrained, small, and fast, fired at the one point where they can
  actually be well-informed — after the reply they depend on exists (or,
  for Icebreakers, once there's nothing yet to depend on but the
  assistant's grounding).

## Consequences

- Two calls instead of one adds a small amount of latency to seeing
  Follow-ups, but not to the reply itself — and that latency is expected
  to be masked by the time it takes to read the reply that just streamed
  in.
- Follow-up/Icebreaker generation is deliberately sequential with the
  reply it depends on, never fired concurrently with it — the reply's
  actual content is the primary signal for what a good Follow-up even is,
  a real dependency rather than an implementation convenience.
- This split is also what makes it safe to run Follow-up/Icebreaker
  generation on its own disposable session rather than the durable
  conversation session — see ADR-0002.
